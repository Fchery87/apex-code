# Spec: LSP — diagnostics as a mutation result, navigation as one deferred tool

**Status:** Landed

| Compatibility posture | **Preserves compatibility.** See below. |

**Compatibility posture.** Every existing tool keeps its name, schema, default
behavior, and `ruleContent` grammar. The session format is untouched. The subsystem is
**off unless configured**: a user with no `lsp` key in `settings.json` gets byte-identical
behavior to today, including an unchanged static prompt prefix, because the one new tool
is registered only when at least one server is configured and resolvable.

Three obligations follow from that posture and are load-bearing rather than incidental:

1. **A workspace with no configured server is not a degraded workspace.** It is the
   current product. Nothing in this spec may make an unconfigured session slower, more
   expensive, or differently shaped.
2. **Diagnostics ride inside recorded tool results, never as synthetic messages.** The
   replay corpus is the only baseline four phases are measured against, and a
   nondeterministic message injected between recorded entries would silently destroy it.
   This is a determinism constraint, not a rendering preference (see Risks).
3. **Servers inherit the sandbox boundary; they do not widen it.** The allowlisted
   CONNECT-proxy egress path and denied host-home are boundaries this spec consumes. A
   language server that cannot work inside them fails visibly, and reaching a new host is
   the user's existing `network.allowedHosts` decision — never a relaxation this
   subsystem performs on its own.

## Executive summary

Apex Code can edit code but cannot tell whether the edit type-checks, so it verifies by
spawning a full build through `bash` — expensive, coarse, and frequently skipped. This
spec adds a language-server subsystem whose primary output is **not a tool**: diagnostics
for a file are collected after every mutation and returned on the `edit`/`write` result
that caused them, costing zero static prompt prefix. A single deferred `lsp` tool covers
the navigation queries grep genuinely cannot answer (`definition`, `references`,
`document_symbols`). Servers are discovered, never downloaded; they run inside the
existing sandbox; and because Apex holds no unsaved buffers, the document-sync model is
disk-based rather than an incremental `didChange` stream.

## Current state

**No LSP code exists.** A case-insensitive search of `packages/*/src` for `lsp`,
`language server`, and `languageserver` returns zero hits. This is not a partial
implementation to finish; it is a subsystem that was scoped, deferred with a stated
reason, and never begun.

**The registry is 15 tools, static prefix 2,150 tokens, ceiling 2,300.**
`createAllToolDefinitions` (`core/tools/index.ts:311`) returns `read`, `bash`, `edit`,
`write`, `grep`, `find`, `ls`, `tool_schema`, `todo_write`, `web_search`, `web_fetch`,
`ask_user`, `plan_present`, `delegate`, `test`. The Phase 4 measurement records 2,706
tokens without deferral and 2,150 with eight first-party tools deferred;
`ENFORCED_PRODUCTION_PREFIX_BUDGET = 2_300` at `test/context/static-prefix.test.ts:40`.

**The 150-token margin is not headroom for new tools, and says so.** The constant's own
doc comment (`static-prefix.test.ts:30-39`) states the margin exists to absorb
"incidental description-wording changes without making this a flaky gate," and that "it
does not budge for a new tool that skips deferral without justification." A new tool is
expected to defer *and* to justify what it spends.

**Every mutation on the shipped CLI path funnels through one function.**
`withFileMutationQueue` (`core/tools/file-mutation-queue.ts:32`) serializes mutations per
resolved real path; `edit.ts:341` and `write.ts:246` are its only callers in
`packages/coding-agent`. There is exactly one place where "a file on disk just changed" is
known — **for the product**, with one qualification below.

**There is a second, parallel tool implementation that this spec does not reach.**
`packages/agent` (`apex-code-agent-core`) ships its own `read`, `write`, `edit`, `bash`,
and a separate `withFileMutationQueue(env, path, fn)` under `src/harness/tools/`, exported
from the package's public API (`packages/agent/src/index.ts:109`). Those factories are
instantiated **nowhere in production** — a repo-wide search finds callers only in
`packages/agent/test/harness/tools.test.ts` — and `packages/coding-agent` imports no tool
factory from `apex-code-agent-core`, only types plus `agent-session` and `create-harness`.
They also carry no `ToolContract`, so they are not registered tools in the Phase 2 sense.
Consequence for this spec, stated rather than discovered later: **an SDK consumer building
on `apex-code-agent-core`'s own edit/write tools gets no diagnostics**, because the hook
lands in `coding-agent`'s tools. Unifying the two implementations is out of scope here and
is a larger question than LSP.

**`buildToolContractSnapshot()` does not exist, so this spec does not cite it.**
`contracts.md` § "One projection, never re-derived" specifies it, the phasing table
assigns it to Phase 4 along with invariant 6 (*"`/tools`, `/doctor`, and generated docs
derive from `buildToolContractSnapshot()` and from nothing else"*), and Phase 4 is marked
**landed**. A repo-wide search returns zero hits for the function, and there are no
built-in `/doctor`, `/tools`, or `/permissions` slash commands — `core/slash-commands.ts:4`
sources commands from `extension | prompt | skill` only. **This is a pre-existing gap
between `contracts.md` and the implementation, not something this spec introduces or
fixes.** It is recorded here because the obvious design — "report server health in
`/doctor`" — cites a surface that is not there, and a spec that did so would be
unimplementable in a way that only surfaces at task 3.

**Apex has no dirty buffers.** Unlike an editor, every mutation is written to disk inside
the tool call that produced it. There is no unsaved state at any point a language server
could be asked a question.

**A tool that spawns a fixed binary already declares what it does, not `exec`.** `grep`
calls `ensureTool("rg", true)` and `spawn(rgPath, args, …)` (`core/tools/grep.ts:190,239`)
while declaring `capabilities: new Set(["fs.read"])` (`grep.ts:142`). This is existing,
shipped precedent, not a new argument invented here.

**Verification today is a build.** With no diagnostics channel, the only way the agent
learns an edit is ill-typed is to run `bash tsc --noEmit`, `test`, or a full build.

## The problem

**1. The verification loop is priced per-build, so it gets skipped.** A single-line edit
whose correctness question is "does this name resolve" costs a whole-project type-check
to answer. The model's options are to pay that cost after every edit, or to batch edits
and pay it once — and batching is what it does, which means errors are discovered several
edits after the one that caused them, with the attribution lost. `bash` declares
`resultRecoverable: false` (`bash.ts:408`), so each of those build outputs is also pinned
in context permanently, which is the expensive half of the same loop.

**2. Grep cannot answer reference questions, and silently returns something anyway.**
"Where is this symbol used" through `grep` returns textual matches: comments, strings,
same-named members of unrelated types, and the definition itself. The failure mode is not
an error — it is a plausible list the model acts on. For a rename or a signature change,
acting on a textually-derived reference set produces a diff that compiles in the file the
agent was looking at and breaks two others.

**3. The one item Phase 4 promised and did not deliver has no owner.** Phase 4's non-goal
named the file, the reason, and the trigger condition ("when the tools below are landed").
All 13 phases now read **landed** in the roadmap table, so there is no future phase whose
scope will pick this up. It is a commitment with a filename and no schedule.

**4. Adding LSP naively breaks the token budget by arithmetic.** At the measured ~77-token
average for a deferred name-plus-description entry, the obvious shape — one tool per LSP
method (`definition`, `references`, `hover`, `symbols`, `rename`, `diagnostics`) — costs
about 460 tokens. Even *two* new deferred tools cost ~154 and land at ~2,304, four tokens
past the enforced ceiling. And the 150 tokens between 2,150 and 2,300 are not available
for this: the constant's comment reserves them as anti-flake slack for wording drift.
Any design that does not confront this ships either a budget-test failure or a quietly
raised ceiling, and the second is worse — it converts a measured gate into a number that
moves whenever it is inconvenient.

## Goals

- [ ] A configured workspace returns diagnostics for a mutated file **on the `edit` or
      `write` tool result that mutated it**, proven end-to-end through a real
      `AgentSession` (`createHarness`), with a test asserting the diagnostic reflects the
      post-mutation content and not the pre-mutation content.
- [ ] The static prefix with the `lsp` tool registered stays under
      `ENFORCED_PRODUCTION_PREFIX_BUDGET` (2,300), asserted by the existing
      `test/context/static-prefix.test.ts` with no change to the constant.
- [ ] A session with **no** `lsp` configuration measures a static prefix byte-identical
to a same-build baseline registry without LSP — the subsystem is provably free when
unused without freezing incidental wording at the historical 2,150 measurement.
- [ ] The `lsp` tool declares all four contract axes, and the registry-wide tests in
      `test/permissions/contract.test.ts` and `test/permissions/gate-universal.test.ts`
      enumerate it without a new exceptions list.
- [ ] `matches(ruleForCall(p), p)` holds for the `lsp` tool (contracts.md invariant 5),
      with at least one negative case: a rule that must *not* match a call it
      superficially resembles.
- [ ] Every current replay-corpus fixture produces unchanged `turnsCompleted` and
unchanged response/tool-result equality with the subsystem compiled in and unconfigured.
- [ ] A configured server that is missing, un-spawnable, or never reaches `initialized`
      **fails fast at startup with an actionable message** naming the binary and the
      lookup path, following `core/permissions/startup.ts`'s precedent; and mutation
      results say diagnostics were unavailable rather than omitting the field.
- [ ] A server that exceeds the restart bound is disabled for the session with a stated
      reason, and a test asserts no unbounded respawn loop.
- [ ] A test asserts a spawned server's egress is bound by the same allowlist as the rest
      of the child — a host absent from `network.allowedHosts` is refused (Linux backend),
      consistent with `test/sandbox/network-allowlist.test.ts`'s existing assertions.
      Starting a language server must not add a host to the allowlist.

## Non-goals

- [ ] **No `rename`, no code actions, no formatting — nothing that returns a
      `WorkspaceEdit`.** This is a permission-model consequence, not a scheduling one. A
      `WorkspaceEdit` mutates a file set that is not known at permission-decision time, so
      `createPathPermissionSpec` cannot authorize it and `ruleForCall` would have to
      return `null` for every call — a tool that is permanently un-generalizable and
      therefore prompts on every invocation. Apex already has `edit` with a working
      grammar. Revisit only with a design for authorizing an edit set discovered *during*
      the call, which is a rule-model change and belongs in its own spec.
- [ ] **No `hover`, `completion`, or `signatureHelp`.** Completion is an
      interactive-editor affordance with no agent consumer — the model emits whole edits,
      not keystrokes. `hover` returns the docstring and type of a symbol the model has
      usually already read. Both cost budget against the ceiling in item 4 to duplicate
      information already reachable through `read`.
- [ ] **Apex does not download language servers.** ADR 0017 requires a reviewed pin —
      exact version, per-platform asset URL, SHA-256, byte size — updated only by source
      change. That regime is proportionate for two tools (`fd`, `rg`) and is not
      proportionate for an open set of servers across platforms maintained by one person
      (ADR 0014). Servers are resolved from `PATH` or an explicit configured path, and a
      missing server fails closed with a diagnostic naming what was looked for and where.
- [ ] **No unsaved-buffer or range-diff synchronization.** Apex sends versioned
      full-content snapshots read from disk. The version orders asynchronous server work;
      it does not create an editable in-memory authority.
- [ ] **No multi-root LSP connection and no sharing across cwd-bound service lifetimes.**
      Each `(server id, canonical root)` gets one single-root process. Sessions created
      from the same `AgentSessionServices`, including delegated children, share that
      service-owned pool; unrelated runtimes do not.
- [ ] **Diagnostics do not gate or block a mutation.** They are reported on the result of
      a mutation that already happened. A diagnostics-gated write would make an
      LSP-configured workspace refuse edits an unconfigured one accepts, which is a
      behavioral fork in the write path for a signal that is advisory by nature.
- [ ] **No `pull`-model diagnostics (`textDocument/diagnostic`).** Push diagnostics
      (`textDocument/publishDiagnostics`) are universally implemented; the pull model is
      not. Supporting both doubles the collector's state machine to reach servers that
      also support push.

## Proposed solution

The design follows from one observation: **the highest-value thing a language server
gives an agent is not a query the agent thinks to make.** It is the answer to a question
the agent did not ask — "that edit you just made does not compile." That reframes the
subsystem's primary output from a tool into a result field, which is also, conveniently,
the only shape that fits the token budget.

### Resolved configuration, ownership, and lifecycle

The subsystem uses one explicit settings shape:

```json
{
  "lsp": {
    "typescript": {
      "command": "typescript-language-server",
      "args": ["--stdio"],
      "languages": [
        { "languageId": "typescript", "extensions": [".ts", ".tsx"] },
        { "languageId": "javascript", "extensions": [".js", ".jsx"] }
      ],
      "rootMarkers": ["tsconfig.json", "jsconfig.json", "package.json"],
      "initializationTimeoutMs": 10000,
      "requestTimeoutMs": 10000,
      "diagnosticsTimeoutMs": 2000
    }
  }
}
```

The `lsp` object is keyed by a stable server id. An entry has `enabled` (default `true`),
a non-empty `command`, `args` (default `[]`), a non-empty `languages` array, ordered
`rootMarkers` (default `[]`), and the three timeouts shown above. Each language mapping
has a non-empty `languageId` and at least one matcher across `extensions` and optional
exact `filenames`. Extensions start with `.`. Matching is case-insensitive on Windows and
case-sensitive elsewhere; exact filename wins before longest extension. Ambiguous equal
matches across enabled entries are startup errors rather than object-order precedence.
Timeouts are finite integers in 100–120,000 ms. Unknown entry keys are startup errors.
Object-key merge follows existing settings behavior: project settings override named
fields of a global entry, arrays replace rather than concatenate, and `enabled: false`
lets trusted project settings disable a global entry.

Both global and trusted-project settings may configure servers. An untrusted project's
settings are already excluded by `SettingsManager`; therefore no executable or arguments
from it are observed or started. Trust prompt copy is amended to name configured language
servers as executable project resources. A command is either a bare executable name resolved against the CLI child's effective
`PATH`, or an absolute path. Relative commands containing a path separator are rejected
because merged settings intentionally lose origin-scope metadata. Resolution freezes the
absolute executable, validates a regular executable file on POSIX, and applies `PATHEXT`
on Windows. No shell is involved and no environment overrides are accepted from LSP
settings.

For a file, canonicalize the path and require it to remain within the canonical session
cwd. Select the sole configured entry whose extension matches. Starting at the file's
parent, walk upward only to the session cwd; at each directory test `rootMarkers` in
configured order. The nearest directory containing any marker wins. If none is found,
the session cwd is the root. Each pool entry is keyed by `(server id, canonical root)` and initializes one process
with one root and `workspaceFolders: null`. Different nested roots therefore use separate
single-root processes; no process is a multi-root client. The cwd-root process is
initialized eagerly at startup, while a nested-root process is initialized on first file
selection under the same attempt policy. Paths and pool keys use canonical paths, with
platform-native case behavior.

The pool belongs to cwd-bound `AgentSessionServices`, not to an individual AgentSession
and not to process-global state. Sessions created from those services, including delegated
children, receive the same injected pool operations; they never own or close it.
`AgentSessionServices.close()` becomes async and `AgentSessionRuntime` awaits it on
replacement and quit. The low-level `createAgentSession()` SDK activates LSP only when a
caller injects those operations, matching its existing delegation pattern; it never
silently creates a process-owning resource that its synchronous `AgentSession.dispose()`
cannot reap. The shipped CLI and `createHarness` use the service-owned path.

Configured entries resolve and initialize their cwd-root process eagerly during service
creation. Any entry that cannot resolve, spawn, or initialize that process within its
timeout produces an error runtime diagnostic and aborts app startup. Nested roots are
not pre-scanned across the workspace; their single-root processes start on first use. After a server has reached
ready, an unexpected exit fails all pending calls and the next demand may restart it.
There are three total spawn attempts per server/root, including the initial attempt and
failed initialization attempts. No immediate crash-loop occurs: restart is demand-driven.
After attempt three fails or later exits, the entry is disabled for that service lifetime;
a fourth spawn is never made. Clean shutdown never restarts.

### Diagnostics are a mutation result, not a tool

`edit` and `write` gain an injectable operations object, matching the pattern
`TestOperations` (`test.ts:28`) and `GrepOperations` (`grep.ts:58`) already establish:

```ts
export interface DiagnosticsOperations {
  /** Diagnostics for a path after a mutation, or an explicit unavailable outcome. */
  afterMutation(absolutePath: string, signal?: AbortSignal): Promise<DiagnosticsOutcome>;
}

export type DiagnosticsOutcome =
  | { status: "ok"; serverId: string; diagnostics: Diagnostic[]; truncated: boolean }
  | {
      status: "unavailable";
      serverId?: string;
      unavailableKind: DiagnosticUnavailableKind;
      reason: string;
    };
```

When LSP is unconfigured for the session, no diagnostics operation is injected and the existing result is returned byte-for-byte. Once the session has at least one configured server, the `unavailable` variant covers both a path with no matching server and a selected server that cannot answer (not ready, timed out, crashed, or disabled). Three properties follow, and each is the reason for the shape:

- **Zero static prefix cost.** The model is not told about a tool; it is told about its
  edit. The Phase 4 budget is untouched by the subsystem's primary feature.
- **LSP stays out of the mutation tools' dependency graph.** A neutral tool-local diagnostics contract is injected into `edit`/`write`; neither imports `core/lsp/*`. Existing edit tests stay deterministic and offline.
- **Once configured for a path, `unavailable` is a value, not an omission.** A silently absent diagnostics field would make a clean edit and an unchecked edit look identical. An entirely unconfigured session remains the compatibility baseline and emits no diagnostics field.

The call sites sit **inside** `withFileMutationQueue` (`edit.ts:341`, `write.ts:246`),
after the write completes and before the queue releases. That placement is what makes the
diagnostic correspond to the content just written rather than racing a subsequent
mutation of the same file.

### Document synchronization and diagnostic freshness

Disk remains the source of truth, but a notification that only says "a file changed" is
not strong enough to attribute a diagnostic to the mutation that caused it. Servers may
publish work computed before `didChangeWatchedFiles`, and `publishDiagnostics.version` is
optional for closed documents. The original draft's watched-file-only design is therefore
rejected.

The pool keeps a configured document open from its first LSP use until pool teardown. On
first use it reads the current disk content and sends `textDocument/didOpen` with version
1. After each successful mutation, while still inside `withFileMutationQueue`, it reads
the just-written disk content and advances the open document to the next integer version.
If the server advertises full sync, `didChange` carries the full text. If it advertises
incremental sync, Apex sends one replacement range covering the entire previous document;
this preserves the same whole-file disk snapshot without implementing edit-diff logic. If
the server advertises no text sync, diagnostics are `unavailable`. When the server asks
for saves, `didSave` follows the change (including text only when requested). Apex does
not also send `didChangeWatchedFiles` for an open document.

A diagnostic waiter is registered before the sync notification so a synchronous publish
cannot race it. A diagnostic result is attributable only when `publishDiagnostics` names
the open file's requested version. A lower version is stale and ignored; a higher version
means the mutation was superseded and returns `unavailable` for the earlier waiter. A server that omits the version does not produce
"clean"—the bounded wait ends as `unavailable` with a reason that the server did not
provide versioned diagnostics. This deliberately prefers a visible limitation over a
plausible stale answer. `didClose` is sent during bounded pool teardown.

There is still no unsaved Apex buffer: every `didOpen`/`didChange` payload is a snapshot
read from disk after the authorized mutation. The client-side version is ordering
metadata, not a second content authority.

### The one tool

```
lsp(input:
  | { operation: "definition" | "references"; path: string; line: number; character: number }
  | { operation: "document_symbols"; path: string })
```

One tool with a discriminated input union, not three tools, because two new deferred
entries already exceed the ceiling by arithmetic (The problem, item 4). `line` and
`character` are one-based UTF-16 code-unit positions at the tool seam and convert to LSP's
zero-based positions; document symbols forbid them. Results normalize to deterministic,
one-based paths/ranges, deduplicate references, expose omitted/truncated counts, and cap
locations at 1,000 and flattened symbols at 2,000. Only `file:` result URIs are returned;
non-file URIs are counted as omitted. The budget is doing design work here and the
constraint is recorded rather than worked around.

| Axis | Value | Why |
| --- | --- | --- |
| `capabilities` | `{"fs.read"}` | See below — this is the one that looks wrong |
| `permission` | `createPathPermissionSpec({ defaultBehavior: "allow", verb: "Query", getPath: p => p.path })` | Read-only over a path; identical grammar to `grep`/`find`/`ls` |
| `context` | `{ resultRecoverable: true, deferSchema: true }` | Re-running the query reproduces it; deferred like every other second-wave tool |
| `evidence` | `{ emits: new Set(), capture: () => [] }` | A navigation query asserts nothing about the workspace |

**`{fs.read}`, not `{exec}` — the argument, because it looks like a ceiling bypass.**
contracts.md § 1.1 treats `exec` as implying the full capability set, precisely so a
parent without `fs.write` cannot delegate to a child with `bash`. An `lsp` tool spawns a
subprocess, so the reflex is to declare `exec` — but the escalation rule's premise is that
*the caller chooses what to run*. Here it cannot: the executable comes from the user's
`settings.json`, the arguments are fixed by the registry, and the wire protocol is
JSON-RPC with a closed method set. The model cannot reach any capability through it that
the tool does not itself expose.

This is exactly `grep`'s existing treatment — it spawns `rg` and declares `{fs.read}`
(`grep.ts:142,190,239`) — and it is stated here rather than left to be discovered during
delegation review, because the alternative reading (declare `exec`) would silently expand
every `lsp`-capable child to the full capability set, which is a real ceiling defect
dressed as caution.

**Server startup is not a tool call.** The pool starts servers out of band, on the
session's own authority, not on the authority of the call that first needs one. A tool
call never spawns a process the permission gate did not see.

### Diagnostics as evidence — requires an ADR

`EvidenceKind` was `"diff" | "test" | "command" | "manual" | "workflow"`
when this spec was written, a settled cross-phase contract (contracts.md § 1.4). A compiler
diagnostic is a source-observed fact about whether a mutation was well-formed, which is
Phase 7's stated purpose — *"distinguish 'the agent said it passed' from 'it passed'"* —
applied to compilation rather than to tests.

ADR 0020 adds `"diagnostic"` with a discriminated `DiagnosticEvidenceRecord`, emitted
by `edit` and `write`. Successful records contain path, selected server, bounded total,
zero-filled severity counts, and a truncation flag. Unavailable records contain a stable
allowlisted classification and a server ID only when the collector obtained a selected connection. Diagnostic
messages and free-form failure reasons never enter durable evidence.

The evidence extension remains severable from LSP.1–5/7, but ADR 0020 accepted it on
2026-08-20 and LSP.6 now implements it.

### Protocol bounds and client responsibilities

The client generates monotonically increasing safe-integer request ids and accepts string
or integer ids on server requests. It validates `jsonrpc: "2.0"` and exactly one of
`result` or a structured `error` on responses; malformed frames fail the client and every
pending request. Headers are ASCII, exactly one `Content-Length` is required, and a header
may not exceed 8 KiB. Inbound and outbound bodies may not exceed 8 MiB. These are fixed safety
bounds, not settings. Stdout parsing stays byte-oriented, stdin honors backpressure and
propagates write errors, and stderr is drained while retaining only a 64 KiB tail for
status/error messages.

Server notifications are exposed through one subscription interface; the diagnostics
collector consumes `textDocument/publishDiagnostics`. The client handles these
server→client requests with fixed, non-interactive responses:

- `workspace/configuration` → an array of `null`, one per requested item;
- `client/registerCapability` and `client/unregisterCapability` → `null` (registrations
  are acknowledged but do not expand Apex's closed method set);
- `window/workDoneProgress/create` → `null`;
- `workspace/workspaceFolders` → `null` (each process is single-root);
- `workspace/applyEdit` → `{ applied: false, failureReason: "Apex Code does not accept server-initiated workspace edits." }`;
- `window/showDocument` → `{ success: false }`;
- `window/showMessageRequest` → `null`;
- workspace refresh requests → `null` without changing the closed capability set.

Every other server request receives JSON-RPC `-32601 Method not found`; it is never
silently ignored. Server-initiated commands and mutations are never executed.

Initialization uses the entry's `initializationTimeoutMs`; timeout, spawn error,
premature exit, invalid framing, or an initialize error kills/reaps the child and consumes
one pool attempt. Ordinary navigation requests use the same timeout and send
`$/cancelRequest` before local rejection. Diagnostics use their separate timeout.
Shutdown gets 2,000 ms for the `shutdown` response, then `exit`; after 500 ms the child
receives `SIGTERM`, and after a final 1,000 ms it receives `SIGKILL`. Pending
non-shutdown calls reject as soon as closing begins. All lifecycle transitions are
serialized, and `dispose()` returns one shared promise.

### Determinism, which is the constraint that shapes the rest

Language servers are asynchronous and indexing-dependent: the same edit can publish
diagnostics in 40 ms on a warm server and 4 s on a cold one, and a server may publish
twice as indexing completes. Three rules keep that out of the replay gate.

1. **Diagnostics only ever appear inside a recorded tool result.** The session JSONL
   records the result; replay reads the recorded value and never re-queries. Nothing is
   injected as a synthetic message between entries, which is what would make a replayed
   turn differ from the recorded one.
2. **The wait is bounded by a fixed budget, and a timeout is an outcome.** The collector
   waits up to a configured budget (default 2,000 ms) for a publish covering the mutated
   URI, then returns `{ status: "unavailable", reason: "timed out after 2000ms" }`. It
   never blocks the mutation indefinitely and never returns "clean" for "did not hear
   back" — those two being confused is the single most damaging failure this subsystem
   can have (see Risks).
3. **No wall-clock value enters a result.** Durations are not reported in result content.
   This follows the same reasoning the Phase 3 spec used to reject time-based eviction:
   any wall-clock dependence needs an injectable clock to keep the replay gate
   deterministic, and the cheaper answer is not to depend on it.

### Sandbox consequences

Apex launches whole-CLI inside the sandbox (ADR 0005), so a spawned server is already a
sandboxed descendant. Three consequences are inherited, not chosen:

- **Outbound network is proxy-mediated and allowlisted — not deny-all.** ADR 0005's
  original text says "denies all direct outbound network," and that is still true of
  *direct* egress, but the proxy bridge its 2026-08-12 amendment scoped has since
  shipped: the child reaches the network only through the supervisor's CONNECT proxy,
  which answers 403 for any host absent from `network.allowedHosts`
  (`core/sandbox/network-proxy.ts`, `network-refusal.ts`), with a default provider-host
  allowlist (`core/sandbox/default-hosts.ts`) and a real settings key
  (`core/settings-manager.ts:93`). **Consequence for LSP:** a server that fetches to
  index (`gopls` against `proxy.golang.org`, `rust-analyzer` against `crates.io`) is a
  *configuration* problem, not an impossibility — the user adds the host. Two things
  still fail regardless, and the spec says so rather than implying the allowlist solves
  everything: a server making raw non-HTTP TCP connections cannot use a CONNECT proxy at
  all, and a server that ignores proxy environment variables will see its direct egress
  denied. Both degrade according to the server's bounded stderr/status output. The existing
  `network-refusal.ts` helper wraps Apex-owned fetches and cannot manufacture an
  actionable host diagnosis for an arbitrary server subprocess.
- **Host home is denied; server caches go to the private state path.** The sandbox policy
  denies host-home and credential directories and mounts private temporary/state paths.
  The registry sets each server's cache/state environment (`XDG_CACHE_HOME` and
  per-server equivalents) into that private path. A server left to default into `~/.cache`
  fails on a denied write, which is a configuration bug the diagnostic must name.
- **Toolchain paths are read-only.** A server that writes into its own installation
  directory is unsupported, and fails visibly.

### Seam invariants

**`beforeToolCall`.** The `lsp` tool passes through the same `evaluateToolCall` as every
other tool, with no bypass and no addition to an exceptions list — contracts.md invariant
2 stays true by enumeration. Diagnostics attached to an `edit`/`write` result are *not* a
tool call and introduce no second execution path: they are computed inside a tool whose
call the gate already authorized, on a file that tool was already authorized to write.

**`ruleContent` is interpreted by the tool.** `lsp` reuses `createPathPermissionSpec`
unchanged. No new grammar is introduced, so the ask prompt
(`core/permissions/responder.ts`, which renders the tool's own `describe()`) presents an
`lsp` rule with the same glob semantics a user already knows from `Read` and `Grep`.

**`transformContext`.** Diagnostics inherit the eviction policy of the result they ride
on: `edit` and `write` are `resultRecoverable: true`, so a diagnostic can be evicted from
context after the model has acted on it. That is correct — the information is
regenerable by re-querying — and it is the reason the evidence extension above matters,
since the evidence ledger is where a diagnostic persists past its context lifetime.

**Evidence is captured by the tool that produced it.** The diagnostic is captured inside
`edit`/`write`'s own execution path from the collector's structured outcome, not
reconstructed by parsing rendered result text. This is ADR 0007's whole point and is why
the evidence extension is scoped to the mutation tools rather than to an observer.

## Risks

**A stale diagnostic is worse than no diagnostic, and looks the same.** If the collector
returns a publish that predates the mutation, the model is told an error it just fixed
still exists, or that a file it just broke is clean. It will act on either. The design
defense is the placement inside `withFileMutationQueue` plus per-URI publish sequencing;
the *signal* is a dedicated test that mutates a file from clean to broken and asserts the
returned diagnostic set is the post-mutation one, and a second that goes broken to clean.
A weaker version of this test — asserting only that *some* diagnostic came back — would
pass against the exact bug it exists to catch.

**"Timed out" rendered as "clean" is the failure that destroys trust in the feature.**
This is why `DiagnosticsOutcome` is a discriminated union rather than an array that is
empty in both cases. The signal is a test asserting a server that never publishes yields
`status: "unavailable"`, and that the rendered result text for that outcome does not
contain the word the clean case uses.

**Cold-start latency lands on the first edit of a session.** A server indexing a large
repository can take tens of seconds to produce a first useful publish, and the 2,000 ms
budget means early edits report `unavailable` while later ones report cleanly — behavior
that reads as flakiness. Mitigation is to start configured servers while creating the runtime's cwd-bound services rather than at first mutation, so indexing overlaps the user's first prompt; the signal is the status
store recording per-server readiness, so "not ready yet" is inspectable rather than
inferred from an empty diagnostic set.

**A crash-looping server burns CPU behind a quiet feature.** The restart bound (default 3
within a session) and session-scoped disable exist for this. The signal is the status
store's disable entry plus a test asserting no respawn past the bound.

**Compiled-in nondeterminism reaching the replay corpus.** The corpus is the baseline
Phases 3, 4, and 7 are measured against, and it must not move because a subsystem was
added. The signal is the corpus itself, run with the subsystem compiled in and
unconfigured; any movement in `turnsCompleted` or result equality fails the gate.

**Scope pressure toward `rename`.** The non-goal above will be re-litigated the first
time someone renames a symbol by hand, and the counter-argument ("just prompt for it")
quietly converts a permission-model gap into a permanent always-ask tool. The defense is
that the non-goal states a *mechanism* failure — `ruleForCall` returning `null` forever —
not a preference, so reopening it requires a rule-model design, not a scheduling decision.

### Amendment (2026-08-19): closure — budget ceiling revised, evidence kind deferred

Tasks LSP.1–5 and LSP.7 landed; LSP.6 did not. Two corrections to claims made above,
both recorded rather than silently edited into the original text.

**The budget claims above ("2,300 tokens," "unchanged at 2,300," "no change to the
constant") no longer hold.** LSP.7's own required measurement — actually configuring
`lsp` against `test/context/static-prefix.test.ts`, which nothing before this had done —
found two things this spec did not anticipate. First, the no-`lsp` baseline had already
drifted from the Phase 4 measurement of 2,150 to 2,292 by the time this work started,
from unrelated tool-description growth across phases 5–8; 142 of the original 150-token
margin was gone before `lsp` added anything. Second, `lsp`'s deferred registration floor
(name, description, and the fixed `DEFERRED_SCHEMA_STUB` announcement overhead) is fixed
at roughly ~72 tokens no matter how short the description gets — of the marginal cost,
only ~8 tokens were recoverable by trimming the description, and narrowing the operation
set recovers nothing at all, since a deferred tool's announced schema is a fixed empty
stub regardless of how many operations its real schema has. This spec's problem
statement item 4 assumed description-shortening would be sufficient; measurement showed
it was not, for reasons upstream of anything this plan controls.

Resolved with the user rather than unilaterally: `ENFORCED_PRODUCTION_PREFIX_BUDGET` is
now **2,500** (2,372 measured with `lsp` registered and deferred, plus a fresh ~5%
anti-flake margin), fixed by the same discipline this spec always intended — a real
number, not an assumed one. See `docs/plans/2026-08-18-lsp.md`'s completed budget
measurement record for the full table. `test/context/static-prefix.test.ts` gained a
second describe block that actually configures `lsp`, closing the gap that let the
pre-existing drift go undetected in the first place.

**LSP.6 (the `"diagnostic"` evidence kind) is deferred, not rejected.** ADR 0020 was
never written — ADR authorship is its own governance decision, and the user chose not to
spend it during this closure. LSP.1–5 and LSP.7 do not depend on it, per this plan's own
severability design; `edit`/`write` continue to emit only `"diff"` evidence. Revisiting
this is a future, separate piece of work, starting from writing ADR 0020.

### Amendment (2026-08-20): diagnostic evidence accepted and implemented

The deferral paragraph above records the state at the 2026-08-19 closure. This
2026-08-20 amendment supersedes it. ADR 0020 was accepted, and `edit` and `write` now
emit a bounded `"diagnostic"` record whenever their injected diagnostics operation returns an
outcome. The durable record excludes diagnostic messages and free-form failure reasons,
uses total plus severity counts so missing or unknown severity cannot look clean, and
marks collector truncation at the 1,000-diagnostic bound. A session with no configured
LSP still injects no diagnostics operation and emits no diagnostic evidence.

**The required 3-OS run earned its place: it caught two real bugs invisible on the
author's Linux machine.** First pass (run 32330913212, Ubuntu + macOS + Windows) found
`LspDiagnostics.afterMutation` keying its publish-diagnostics waiter off the caller's raw
input path while `sync.synchronize()` opens the document under the registry's
*canonicalized* path — identical on Linux, divergent on macOS (`/tmp` resolves through
`/private`), so every `afterMutation` call timed out on macOS only. Fixed by keying the
waiter off the canonical path throughout. Second pass (run 32331728170) confirmed that
fix and found a second, Windows-only bug: three pre-existing test files called the
now-`async` `AgentSessionServices.close()` without awaiting it inside a synchronous
cleanup stack, racing a `state.sqlite` file deletion against a still-open handle — silent
on POSIX, a hard `EBUSY` failure on Windows's stricter file locking. Fixed by awaiting
each cleanup. Third pass (run 32332670645) is green: no `test/lsp/*` or
`test/observability/*` failure on any of the three OSes, only the three pre-existing,
unrelated `splash-header.test.ts` failures already present on the pre-LSP baseline.
