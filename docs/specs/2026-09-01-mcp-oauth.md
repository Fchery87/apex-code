## Executive summary

Streamable-HTTP MCP servers that require OAuth become usable through the host's existing
credential store, not a second one. `/mcp auth <server>` runs the MCP authorization
handshake — protected-resource discovery, dynamic client registration when the server
advertises it, authorization-code with PKCE — against a loopback listener that exists only
for the duration of the flow. Access and refresh tokens land in `auth.json` under
`mcp/<server>`, protected by the store's existing cross-process lock; the connector reads
them the way it reads a bearer env var today; and an expired access token is refreshed
through the supervisor-mediated credential-write channel ADR 0015's first amendment built
for exactly this. A tool call never starts an OAuth flow on its own.

## Context and motivation

- `docs/specs/2026-08-28-native-mcp.md` (Non-goals) deferred this work with its own
  trigger: "OAuth gets its own spec once the contract and lifecycle are proven." Native
  MCP landed 2026-08-30 (13 of 13 tasks, three-OS CI green) and has been in use since;
  the trigger is satisfied and this spec is the re-decision that was promised.
- The original non-goal named two objections — "the callback server, and a credential
  store" — and this spec answers both directly: the credential store is the existing one
  (§ Credential custody), and the callback server is a flow-scoped loopback listener
  (§ The flow), not a standing service.
- `docs/adr/0015-host-owned-credential-handoff.md` is the load-bearing ADR, twice over.
  Its base decision makes credentials host-owned with an explicit read-only projection.
  Its 2026-08-22 amendment anticipates this work by name: "The supervisor holds the host
  credential lock across the child's `modify` callback, so **OAuth refresh and login**
  retain `CredentialStore`'s cross-process serialization contract." This spec is that
  sentence, made concrete.
- The same ADR's 2026-08-28 amendment (git credentials) supplies the pattern for what may
  cross the sandbox boundary: a narrow, reachable, human-gated answer to one question —
  never a store, a file, or an ambient environment variable.
- `docs/adr/0013-no-unowned-hosted-service-defaults.md` is unaffected: authorization
  servers are reached only because the user configured the MCP server and ran the auth
  command. `docs/adr/0023-supervisor-owned-escalation-authority.md` sets the shape of the
  user-initiation rule in § Authority.

## Current state

- `packages/coding-agent/src/core/mcp/types.ts` — the HTTP transport config carries
  `headers`, and `bearerTokenEnv` with the comment "OAuth is a spec non-goal (ADR 0015)".
  That comment is the recorded deferral this spec retires.
- `packages/coding-agent/src/core/mcp/connector.ts` — headers are assembled per
  connection: static `headers` plus `Authorization: Bearer <process.env[bearerTokenEnv]>`
  when configured. The token is read from the environment at call time.
- `packages/coding-agent/src/core/auth-storage.ts` — the host credential store
  (`auth.json`) with `withLock` / `withLockAsync` cross-process serialization. This is
  where provider tokens already live; ADR 0015's projection and write channel are built
  around it.
- A 401 from an OAuth server today surfaces as a failed `mcp` tool call with no path to
  recovery except editing config to name a bearer env var — which most hosted servers
  cannot accept, because they issue tokens only through OAuth.

## The problem

The MCP ecosystem's hosted servers standardize on OAuth 2.1 with the MCP authorization
extensions (protected-resource metadata, dynamic client registration, PKCE, resource
indicators). Version one's env-var bearer token covers self-hosted gateways and nothing
else, so the deployed ecosystem is unreachable in practice: the user cannot obtain a
static token to point `bearerTokenEnv` at. The gap is not convenience. It is the
difference between "Apex speaks MCP" and "Apex speaks MCP to the servers people actually
run."

Building this naively would violate two settled ADRs — a second credential store
contradicts ADR 0015, and an OAuth flow that starts itself mid-session would put an
outbound-authentication decision in the hands of whatever the session is doing, which
ADR 0023's escalation posture exists to prevent. The design below is shaped so that
neither ADR needs an amendment.

## Goals

- [ ] `/mcp auth <server>` completes authorization-code + PKCE against a server advertising
      the MCP protected-resource metadata, and the next `mcp` call succeeds with no
      environment variable configured.
- [ ] Tokens are stored under `mcp/<server>` in the existing host credential store, and no
      new credential file, directory, or store is created anywhere.
- [ ] The loopback listener binds `127.0.0.1` on an ephemeral port, accepts exactly one
      callback carrying the issued `state`, and is closed before the command exits —
      asserted by a test that scans for listening sockets after the flow.
- [ ] A 401 from an OAuth-configured server during a tool call fails closed with a
      structured result naming `/mcp auth <server>`; no OAuth endpoint is contacted from a
      tool call path.
- [ ] A sandboxed child refreshes an expired access token only through the
      supervisor-mediated write channel, with the host holding the store lock across the
      write; a child with no channel fails closed to the structured 401 result.
- [ ] With no OAuth-configured server, the static prompt prefix, `getActiveToolNames()`,
      and every existing MCP test are unchanged.

## Non-goals

- [ ] **Device-code flow and non-loopback redirects.** One flow, the one the MCP
      authorization spec standardizes; device code adds a second polling surface with no
      user asked for it here.
- [ ] **OAuth for stdio servers.** A stdio server inherits the user's environment and
      authenticates itself; there is nothing in-process to authorize.
- [ ] **Token sync across machines, shared caches, and an SSO layer.** Tokens are
      host-local state in a host-local store, same as provider credentials today.
- [ ] **New auth schemes beyond OAuth** (mTLS, signed headers, API-key provisioning).
      Static `headers` already covers static secrets.
- [ ] **Server-initiated sampling/elicitation and resources/prompts as surfaces.** Still
      governed by the native-MCP spec's non-goals; nothing here touches them.

## Proposed solution

| Component | Decision | File(s) |
| --- | --- | --- |
| Config | `auth: "oauth"` on an HTTP server entry (absent = today's behavior). The server's `url` is the OAuth resource identifier; `resource` is sent on every authorization request per the MCP spec. | `core/mcp/types.ts`, `core/mcp/config.ts` |
| Authority | Only `/mcp auth <server>` starts a flow (CLI subcommand; TUI command wraps it). It is an explicit host-side user action, the same class of action as `/login` — never a sandbox-child action, never a tool-call side effect. | `src/cli/` command, `modes/interactive/` command |
| Discovery | 401 + `WWW-Authenticate` → protected-resource metadata (RFC 9728) → authorization-server metadata. Metadata URLs must be `https`. No metadata: the command fails with the server's challenge in the error. | `core/mcp/oauth/discover.ts` (new) |
| Client registration | Dynamic registration (RFC 7591) when the authorization server advertises the endpoint; otherwise the error prints the redirect URI to register manually and where to put the client id. | `core/mcp/oauth/register.ts` (new) |
| The flow | Authorization-code + PKCE (S256), single-use `state`, loopback redirect to `http://127.0.0.1:<ephemeral>/callback`. The listener binds only inside the command, times out at five minutes, and prints the authorization URL for headless use before trying to open a browser. | `core/mcp/oauth/flow.ts` (new) |
| Credential custody | Access + refresh tokens stored via the existing store API under key `mcp/<server>`, written inside `withLockAsync`. No second store, no cache file, no session artifact. | `core/auth-storage.ts` (consumed, barely changed) |
| Connection use | `connector.ts` resolves, in order: static `headers`, then `bearerTokenEnv`, then the `mcp/<server>` store entry when `auth: "oauth"`. In a sandboxed child the store entry arrives through ADR 0015's read-only projection, named explicitly by the server's config — the same "limited to what the config requires" rule as provider variables. | `core/mcp/connector.ts` |
| Refresh | Expired access token: the process holding the connection attempts refresh and persists the rotation through the supervisor-mediated write channel (`core/sandbox/rpc/`), host-side lock held per the 2026-08-22 amendment. The token endpoint is persisted alongside the tokens, so refresh does not re-discover; discovery is only the fallback. No channel (non-sandbox host does it directly; enforcing sandbox without the channel) → structured 401 result naming the auth command; never a silent retry loop. | `core/mcp/connector.ts`, `core/sandbox/rpc/` (consumed) |
| Failure shape | The structured result distinguishes "never authorized", "expired and refresh failed", and "server refused" so the user's next action is unambiguous. | `core/mcp/connector.ts` |

## Risks

- **A loopback listener is a new inbound surface.** Mitigations: binds `127.0.0.1` only,
  ephemeral port, exists only inside the auth command, single-use `state` check, five
  minute timeout, closed in a `finally`. The test in Goals asserts the socket is gone.
- **Malicious metadata.** Discovery accepts `https` metadata URLs only, with one
  deliberate exemption: loopback `http` (127.0.0.1/localhost/::1), which the
  authorization flow itself needs and local development servers ride on. Discovery
  never follows a redirect across schemes; the resource parameter pins tokens to the
  configured server URL so a confused-deputy exchange yields a token useless elsewhere.
- **Token bytes in child memory.** Accepted, and unchanged from today's `bearerTokenEnv`
  shape: the projection already places exactly the named credential in the child. What
  this spec refuses is making tokens ambient or child-writable — the write path stays
  supervisor-mediated, audited, and lock-serialized.
- **Refresh races across processes.** Handled by construction: every write goes through
  the store's lock, and rotation conflicts re-read before retrying once, then fail to the
  structured result.

## Deletion inventory

- The comment on `bearerTokenEnv` in `packages/coding-agent/src/core/mcp/types.ts`
  ("OAuth is a spec non-goal (ADR 0015)") becomes wrong the moment this lands and is
  rewritten to point here. `bearerTokenEnv` itself stays: it is the right shape for
  static tokens and remains the zero-dependency path.
- Nothing else. No roadmap row, ADR, or prior spec is obsoleted; the native-MCP spec's
  non-goal is honored by this document, which is the follow-up it asked for.
