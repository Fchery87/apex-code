## Order changes

**Two tasks move ahead of the value milestone, against the spec's suggested Rollout
order.** The spec proposed: pool → diagnostics → settings → tool → sandbox → evidence.
This plan runs: pool → settings → sandbox → diagnostics → tool → evidence.

The reason is that the spec's order ships the value milestone (diagnostics) while the
spawn environment is still wrong for a real server. A stub server needs no cache
directory and makes no egress, so diagnostics-against-stub would pass its tests and then
fail on the first real `typescript-language-server`, which writes a cache into a path the
sandbox denies (`~/.cache`, denied host-home per ADR 0005). Getting the spawn environment
right is a property of the thing that spawns, so it belongs with the pool, not three
tasks later. Settings moves up for the same reason: without it the subsystem is
configurable only from test code, so LSP.4 could not be dogfooded on this repository the
day it lands.

Cost of the change, accepted: the first user-visible behavior arrives at task 4 of 7
rather than task 2 of 6. That is a worse demo and a better first real run.

## Review decisions resolved before the pool slice

The initial review found decisions the draft had left implicit. They are now settled in
the spec's **Resolved configuration, ownership, and lifecycle**, **Document
synchronization and diagnostic freshness**, and **Protocol bounds and client
responsibilities** sections:

- one exact keyed settings shape, existing trusted-project boundary, no configured env or
  shell, and executable resolution in the effective child environment;
- canonical containment plus deterministic extension and nearest-root-marker selection;
- eager configured-server initialization owned by cwd-bound `AgentSessionServices`, with
  async runtime teardown and shared use by delegated sessions;
- three total demand-restarted spawn attempts, fixed initialization/request/shutdown
  timeouts, bounded framing/stderr, and explicit fixed server-request responses;
- versioned open documents with whole-document synchronization (full text or one full
  replacement range according to server capability); watched-file-only freshness is
  rejected, and versionless publishes return `unavailable` rather than a stale answer;
- no diagnostics injection or result change whatsoever when `lsp` is unconfigured.

These are implementation decisions, not open questions. A later task may amend them only
by updating the spec and this order-change record before code diverges.

## Task LSP.1 — registry, client, pool

### Red

1. Add the stub language server — a small in-repo JSON-RPC responder over stdio, scripted
   per test. It is the fixture every later task reuses; build it here, not inline in
   LSP.4.
2. Assert the `initialize` → `initialized` handshake completes and that a request issued
   before `initialized` is queued rather than lost.
3. Assert request/response correlation under interleaving: two in-flight requests resolve
   to their own results, and a `$/cancelRequest` abandons one without disturbing the
   other.
4. Assert the restart bound: a server that exits three times within a session is disabled
   and not respawned a fourth time.
5. Assert teardown: `shutdown` then `exit`, and no orphaned child after session end.

### Green

Implement `core/lsp/registry.ts` (validated config → frozen executable, language
matchers, and nearest-root resolution; bare `PATH` or absolute path only, **no download**),
`core/lsp/client.ts` (bounded JSON-RPC 2.0 framing, closed server-request dispatcher,
notification subscription, initialization and teardown), and `core/lsp/pool.ts` (cwd-root
eager startup, nested-root demand startup, three total attempts per key, session-scoped
disable, teardown). Config is injected directly at this stage; the settings surface is
LSP.2. A failed initialize consumes an attempt; failed children are killed and reaped.

### Refactor

Keep the wire protocol in `client.ts` and lifecycle policy in `pool.ts`. The client must
not know about restart bounds and the pool must not parse JSON-RPC — LSP.4's collector
subscribes to a publish stream, and that seam is only clean if these two stay separate.

## Task LSP.2 — settings, startup resolution, status store

Add the spec's keyed `lsp` settings shape to `core/settings-manager.ts`: command, argv,
enabled flag, language-id filename/extension matchers, root markers, and initialization,
request, and diagnostics timeouts. Validate unknown keys, timeout bounds, ambiguous
matchers, and the bare-or-absolute command rule at startup.

Resolution failure fails fast at startup with an actionable message naming the binary and
the lookup path, following the precedent in `core/permissions/startup.ts` — *"a
misconfigured non-interactive run should fail fast, at startup, with an actionable
message — not deny every tool call mid-run in a way that looks like a bug."* A configured
server that cannot be found is that same class of misconfiguration.

Add `core/lsp/status.ts`: a bounded, per-session record of each server's state (resolved /
ready / degraded / disabled, with reason), modelled on `core/sandbox/violations.ts`.

**This is not a `/doctor` task.** `/doctor` does not exist, and neither does
`buildToolContractSnapshot()` — see the spec's Current state. The status store is
inspectable structured state; wiring it to a user-facing command is out of scope and is
blocked on a surface this plan does not build.

## Task LSP.3 — sandbox spawn environment and egress

Prove that servers inherit the existing sandbox launch environment, which already points
`HOME`, `TMPDIR`, and the XDG config/cache/data/state variables at the private sandbox
state path. Add no per-server environment setting unless the inheritance test exposes a
real gap; LSP settings never accept arbitrary environment overrides.

Prove egress with a real-`bwrap` test in the style `test/sandbox/network-allowlist.test.ts`
already establishes: a host absent from `network.allowedHosts` is refused for a server
child exactly as for any other child, and **starting a language server adds no allowlist
entry**. The second assertion is the one that matters — it is what keeps this subsystem
from quietly widening the boundary it claims to inherit.

No change to `core/sandbox/policy.ts`, `network-proxy.ts`, or `default-hosts.ts`. If this
task finds itself editing sandbox policy, the design is wrong and the spec's third
compatibility obligation has been violated.

## Task LSP.4 — diagnostics collector and the mutation hook

**The value milestone.** After this task the feature is worth having; everything after is
addition.

### Red

1. **Clean → broken.** Mutate a file from well-formed to ill-formed through a real
   `AgentSession` (`createHarness`, `test/test-harness.ts`) and assert the returned
   diagnostics describe the post-mutation content. Then **broken → clean**, asserting the
   set empties. A weaker test asserting only that *some* diagnostic returned would pass
   against the exact staleness bug this exists to catch (spec, Risks).
2. **Timeout is not clean.** A stub that never publishes yields
   `{ status: "unavailable", reason: … }`, and the rendered result text for that outcome
   does not contain the word the clean case uses.
3. **No LSP configuration** injects no diagnostics operation and returns byte-identical existing `edit`/`write` results. A configured path whose server is unavailable returns the explicit `unavailable` variant.
4. **Ordering.** Two mutations to the same path in flight resolve to their own
   diagnostics, exercising the `withFileMutationQueue` placement.

### Green

Implement `core/lsp/diagnostics.ts` plus the sync manager: register a waiter before
versioned whole-document synchronization, accept only the exact-version publish, cap
validated diagnostics, and return the `DiagnosticsOutcome` discriminated union. Missing
versions, supersession, crash, unsupported sync, and the default 2,000 ms timeout are
explicit `unavailable` outcomes. Add the injected `DiagnosticsOperations` to `core/tools/edit.ts` and
`core/tools/write.ts`, matching the existing `TestOperations` (`test.ts:28`) /
`GrepOperations` (`grep.ts:58`) pattern, remaining absent when LSP is unconfigured.

The call site sits **inside** `withFileMutationQueue` (`edit.ts:341`, `write.ts:246`),
after the write completes and before the queue releases.

### Refactor

`edit.ts` and `write.ts` import the `DiagnosticsOperations` interface and nothing from
`core/lsp/*`. Verify by inspection that no `core/lsp` import appears in either file — that
separation is what keeps existing edit/write tests deterministic and offline.

No wall-clock duration enters result content (spec, Determinism rule 3).

## Task LSP.5 — the `lsp` tool, grammar, and budget

One tool with a discriminated union: definition/references require one-based UTF-16
`line`/`character`, while document_symbols forbids them. It declares `deferSchema: true`,
`capabilities: {"fs.read"}`, and permission via `createPathPermissionSpec` with
`defaultBehavior: "allow"`. Normalize/cap results exactly as the spec defines.

Registered **only when at least one server is configured and resolvable**, which is what
makes the spec's "byte-identical prefix when unconfigured" goal achievable.

Red before green: the registry-wide invariants in `test/permissions/contract.test.ts` and
`test/permissions/gate-universal.test.ts` must enumerate it without a new exceptions list;
`test/permissions/lsp-rules.test.ts` proves `matches(ruleForCall(p), p)` (contracts.md
invariant 5) **and** a negative case — a rule that must not match a call it superficially
resembles.

The `{fs.read}`-not-`{exec}` decision is settled in the spec and is not reopened here. Its
test is the delegation-ceiling assertion: an `lsp`-capable child must not thereby acquire
the full capability set.

**The first real 3-OS CI run (32330913212) found a genuine cross-platform bug this
plan's own author-machine testing (Linux) could not see.** `core/lsp/diagnostics.ts`'s
`afterMutation` computed its waiter's URI from the caller's raw input path, while
`sync.synchronize()` opens the document under `connection.selection.path` — the
registry's *canonicalized* form (symlinks resolved). On Linux these are usually the same
string, so the mismatch was invisible; on macOS, where `$TMPDIR`/`/tmp` resolve through
`/private`, they differ, so the waiter's key never matched the stub server's published

macOS-only failure). Fixed by keying the waiter off `connection.selection.path`
throughout, not the raw argument. The same raw-vs-canonical gap also broke three
assertions in `test/lsp/registry.test.ts` and `test/lsp/pool-lifecycle.test.ts` that
compared registry/pool output against the *raw* mkdtemp path instead of its canonical
form; fixed the same way registry.ts itself resolves paths (`realpathSync`, falling back
to `resolve`). Re-run: [pending — record the green run id here once confirmed].

## Shared implementation rules

- Write the failing test before each implementation slice; run the narrowest test first.
- Tests use the **stub server**, not a real `tsserver`. A real server makes the suite
  depend on an installed toolchain, install-time network, and that server's own indexing
  latency — three sources of flake for a suite whose subject is Apex's client. One
  optional real-server integration test may exist outside the required gate.
- Tests that drive sessions or write state use `mkdtemp`/`chdir` and clean up; no test
  writes to this repository's own `.apex-code` state.
- No task edits `core/sandbox/policy.ts`, `network-proxy.ts`, or `default-hosts.ts`. This
  subsystem consumes the boundary and never widens it.
- No wall-clock value enters a tool result. Time-dependence needs an injectable clock to
  keep the replay gate deterministic; the cheaper answer is not to depend on it.
- Every new tool declares all four contract axes. Rule tests carry positive and negative
  cases; `null` from `ruleForCall` is asserted where a call is not generalizable.
- Do not implement `rename`, code actions, or formatting. The spec declines them on a
  mechanism failure (`ruleForCall` returns `null` forever), not on schedule, so adding
  them is a rule-model change and not this plan's to make.

## Budget measurement record (completed in LSP.7)

The `lsp` tool's prefix cost is measured, not assumed — the same discipline Phase 4 task
4.7 applied.

| Measurement | Result |
| --- | --- |
| Baseline prefix, no `lsp` configured (same-build pre-LSP comparison) | 2,292 |
| Prefix with `lsp` registered and deferred | 2,372 |
| Prefix with `lsp` registered and **not** deferred | 3,203 |
| Headroom against the original 2,300 ceiling | **-72 (over budget)** |

The measurement found two things, not one. First, the no-`lsp` baseline had already
drifted from the Phase 4 measurement of 2,150 to 2,292 — 142 of the original 150-token
anti-flake margin consumed by unrelated tool-description growth across phases 5–8, before
this plan touched anything. Second, `lsp`'s own deferred registration cost is ~80 tokens
(name, description, and the fixed `DEFERRED_SCHEMA_STUB` announcement overhead), of which
only ~8 tokens were trimmable by shortening the description — the rest is a fixed
per-tool cost that narrowing the operation set does not touch at all, since a deferred
tool's announced schema is a fixed empty stub regardless of how many operations its real
schema has. Between drift and the fixed floor, no description-only fix could close the
gap; the ceiling itself was stale.

Resolution, decided with the user rather than unilaterally: re-measure and raise the
ceiling the same way Phase 4 originally fixed it — from a real number, not a round one
picked in advance. `test/context/static-prefix.test.ts`'s `ENFORCED_PRODUCTION_PREFIX_BUDGET`
is now **2,500** (2,372 measured + ~5% fresh anti-flake margin), and a new test in that
file (`"production static prefix with lsp configured"`) actually configures `lsp` and
asserts against it — closing the exact gap that let the pre-existing drift go undetected,
since the original test suite never configured `lsp` and so never measured this path at
all until this record was completed.
