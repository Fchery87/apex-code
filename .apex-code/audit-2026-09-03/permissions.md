## Flow before critique

1. `main.ts:661-670` requires an explicit mode for non-interactive sessions. Interactive runs can start in `default`. `main.ts:825-833,903-908` builds the real file store and injects the gate into sessions. `--allowedTools` creates tool-wide `cliArg` allow rules, not a tool allowlist.
2. `permissions/store.ts:160-231` reads managed policy, local, project, and user files on each snapshot. Source is assigned from the file, not trusted from JSON. Flag/CLI rules and runtime command/session rules join that snapshot. Parse/read errors block every call in `gate.ts:57-64`.
3. `rules.ts:76-100` selects the highest matching source: policy > flag > local > project > user > cliArg > command > session. It asks each tool to match rule content. Specific content beats a blanket at the same source. Longer content then lexical order breaks other ties.
4. `modes.ts:42-69` applies the plan floor before policy, preserves matching policy rules, then applies bypass. `acceptEdits` only auto-allows edit-shaped capabilities when no rule matched. Plan denies `fs.write`, `exec`, and `delegate`, but permits explicit state/UI work. This matches the updated tool-surface spec, not the older comment saying every state mutation is denied.
5. `agent-loop.ts:665-708` prepares and validates arguments. `agent-session.ts:675-728` runs extension handlers, then declarative hooks, then the gate. A blocking extension/hook stops the call. A nonblocking extension input mutation still reaches the gate. `agent-loop.ts:728-731` executes the same validated argument object after approval. Handler errors become tool errors, not implicit approval.
6. `gate.ts:74-97` asks the responder only for an ask result. No responder or a declined prompt blocks. Always-allow writes a session-source rule generated by the tool. This dies with the store, although the UI label does not say that.
7. Path tools compare cwd-relative globs. Bash classifies shell segments, rejects unsupported grammar from scoped matching, and requires every segment to match one rule.
8. `sdk.ts:498-562` computes the parent's capabilities from active tools and creates children in-process with a derived live store and the parent's mode getter. The child has no responder. `delegation/runtime.ts:129-166` rejects depth or capability violations before construction. `DerivedPermissionRuleStore` rejects file-backed `apply` destinations. Session registry construction filters child tools against its allowlist at `agent-session.ts:3317-3333`.

## Confirmed findings

### P1. High: untrusted project files can grant permissions

Actor: a repository author, or someone who can change checkout-local files. No trusted extension is needed.

Evidence: `core/trust-manager.ts:30-38,185-193` does not list either permission file as a trust-requiring resource. `main.ts:772-777` passes trust into settings but `main.ts:825-833` constructs the permission store without it. `permissions/store.ts:164-166,198-231` always reads both project scopes and their modes.

Consequence: a checkout containing only `.apex-code/permissions.json` can select `bypassPermissions` in an interactive launch with no explicit flag. Even an explicit `--permission-mode default` does not stop project allow rules from granting bash. A user denial at lower precedence can be overridden by this untrusted file. Managed policy still wins when it matches.

Probe: a temp project with only a permission file produced `permission-only project needs trust false` and `permission-only project mode bypassPermissions`. Actual main caller inspection establishes that this store is used regardless of the trust decision.

Remedy: pass a live trust decision into permission loading. Ignore project/local grants and modes until trust is accepted. Include both permission paths in trust-resource detection. If untrusted restrictions remain useful, support restriction-only loading rather than interpreting untrusted allows.

### P2. High: write-capable agents can rewrite their own authorization

Actor: prompt-injected model in `acceptEdits`, or a child allowed broad workspace writes. No shell grant needed.

Evidence: `modes.ts:31-39,66-68` auto-allows write. `tools/write.ts:225-230,253-277` has no protected-path guard and writes arbitrary paths. `permissions/store.ts:165-166,198-231` rereads those same workspace files. The sandbox places user state under the writable workspace at `sandbox/cli-launch.ts:281-282,338`.

Consequence: writing `.apex-code/permissions.local.json` with a bash allow upgrades edit authority to shell authority on the next call. Existing lower-precedence bash denials do not help. A derived child's `apply()` restriction does not stop its ordinary write tool from changing the parent's backing files. This defeats the practical child-overlay isolation claimed by ADR 0008. Matching managed policy and plan's hard write floor remain protections.

Probe: after a user-source bash deny, the gate allowed writing the local permission file in `acceptEdits`; the real write tool wrote it; the next bash decision was `{ block: false }`.

Remedy: keep security configuration outside model-writable roots or mount it read-only. Treat edits to security files as a distinct, operator-only action. Apply protection to aliases and resolved targets, not only the literal path. Do not rely only on store `apply()` restrictions.

### P3. High: path normalization mismatch bypasses explicit denials

Actor: a model that can choose tool arguments. Prerequisite: a path-specific deny, with reads otherwise allowed or writes otherwise permitted.

Evidence: `tools/path-permission.ts:24-36` calls `formatPathRelativeToCwdOrAbsolute`. `utils/paths.ts:102-121` does not request `stripAtPrefix` or Unicode-space normalization. Execution does both in `tools/path-utils.ts:40-49`. Read uses `resolveReadPathAsync` at `tools/read.ts:258`, with further filename fallback at `path-utils.ts:86-117`.

Consequence: deny `read(secret.txt)` does not match `read({path:"@secret.txt"})`, but the tool reads `secret.txt`. This bypass needs no symlink or external race. The same resolver mismatch applies to writes and edits using `resolveToCwd`.

Probe: direct path blocked; `@secret.txt` allowed; real read returned the temp sentinel text `private`.

Remedy: resolve the operation target once before authorization, then use that exact resolved target for matching and execution. Include read's alternate-file resolution in that boundary. Add public tests for @ prefixes, Unicode spaces, and fallback filenames.

### P4. High: scoped bash denials disappear for mixed or unsupported commands

Actor: a model choosing bash input. Prerequisite: a scoped high-precedence deny with a lower-precedence blanket allow, or bypass mode. For example managed deny `touch:*` plus user allow bash.

Evidence: `tools/bash.ts:128-138` uses the same all-segments matcher for allow and deny. `rules.ts:50-51,84-85` discards any nonmatch regardless of behavior. Unsupported shell input also returns false. `modes.ts:53-57` protects policy only when a policy rule actually matched.

Consequence: policy denies `touch denied`, but permits `echo ok; touch denied` or `touch denied > output` when the lower blanket allow applies. Parser conservatism only prevents scoped allows; it does not make the overall decision fail closed. This contradicts ADR 0004's assurance that unmodeled grammar resolves to ask, never allow, in the presence of broad lower rules.

Probe: direct command blocked; mixed chain and redirected command both returned `{ block: false }`. No destructive shell command ran in this probe.

Remedy: expose a richer tool match result. Allow requires all segments covered; deny must detect any prohibited segment. Unknown grammar must preserve an unresolved restriction and prevent a lower allow from clearing it. Keep tools responsible for their grammar.

### P5. Medium: generated path grants are globs rather than exact paths

Actor: a model that gets one persistent session approval for a filename containing glob metacharacters. Such names are valid on Linux.

Evidence: `tools/path-permission.ts:29-36` returns the raw normalized filename from `ruleForCall`, then interprets it through minimatch. `gate.ts:90-95` persists it unchanged.

Consequence: approving the literal file `*.txt` can authorize every matching sibling. Brackets and other minimatch syntax also make some generated rules fail to match the originally approved filename. The comment promising "only that path" is false.

Probe: generated rule was `*.txt`; matching it against `other.txt` returned true.

Remedy: encode exact-path grants distinctly, or escape all grammar metacharacters in generated paths. Test both roundtrip and non-expansion properties with unusual real filenames.

### P6. Medium: symlinks bypass path-target restrictions

Actor: repository author who can provide a symlink, or a model with a pre-existing alias. Prerequisite: target is reachable inside the OS sandbox.

Evidence: `utils/paths.ts:102-121` normalizes lexically, without `canonicalizePath`. Path permission matching uses that result. The default write operation uses normal `fs.writeFile` at `tools/write.ts:54-56`, and read follows the ordinary filesystem target.

Consequence: a deny on `secret.txt` does not restrict reading `alias.txt -> secret.txt`. A grant to `safe/**` can also include a symlink leading outside that subtree. The OS sandbox can still prevent leaving its writable/readable roots, but does not enforce the finer permission rule inside those roots.

Probe: a temp symlink to the denied file was allowed by the gate.

Remedy: authorize resolved targets, including the nearest existing ancestor for creation. Guard final opens against symlink races if this is intended as a security boundary. Document a lexical-only scope explicitly if that weaker guarantee is intentional.

### P7. High: bash exact grants collapse significant quoted whitespace

Actor: a model after one session-persistent approval of a shell-interpreter command. No prefix grant is needed.

Evidence: `tools/bash.ts:79-80` normalizes every whitespace run with `replace(/\s+/g, " ")`, including quoted content. Both `segmentMatchesRule` and `ruleForCall` use this normalization at lines 91-99 and 147-153. The classifier correctly preserves quoted newlines, but the matcher then destroys that distinction.

Consequence: an exact approval of `sh -c 'echo safe # comment touch marker'` also permits `sh -c 'echo safe # comment\ntouch marker'`, where `\n` is a real newline. The first only prints. The second runs `touch marker` because the newline ends the inner shell comment. "Always allow this" silently approves a different inner program.

Probe: generated the rule from the first command, confirmed that the second matched it, then executed both through the real local shell operations in a temp directory. Output was `marker after original false` and `marker after changed input true`.

Remedy: preserve quoted bytes in exact grants. Prefer storing the exact command text for `ruleForCall`; any normalization must be performed by a shell-aware token representation that preserves quoted argument values. Test quote-contained newlines, tabs, and multiple spaces with commands that interpret their string arguments.

## Additional concerns and accepted limits

- Same-source equal-content rules are order-dependent. `rules.ts:61-68` returns equality without comparing behavior; `resolvePermission` keeps the first. Probe: allow then deny yields allow; reversed yields deny. `addRules` appends at `store.ts:117-118`, so appending a duplicate deny does not revoke an earlier allow. This is a confirmed low-severity correctness issue, not a new precedence-source bypass. Reject contradictory duplicates, replace by key, or specify a security-safe tie rule. The current comment promising array-order independence is too broad.
- PowerShell reuses the bash permission grammar through `powershell.ts:49-56` and `createShellToolDefinition`. A crafted PowerShell command `Write-Output "x\"; New-Item hacked; #"` matches `Write-Output:*` in the bash matcher because backslash escapes a quote only in bash. PowerShell does not use backslash as its quote escape. This is a high-risk hypothesis with a confirmed matcher mismatch, not an executed PowerShell exploit here. `command -v pwsh` exited 1. Give PowerShell its own conservative grammar or reject scoped grants until it has one.
- SDK sessions can omit the gate. This is documented at `agent-session.ts:277-285`, not a hidden CLI bypass. The invariant "every tool invocation passes the gate" needs this SDK opt-out qualification. Malicious trusted extensions have arbitrary in-process code already; deferred mutation by such code is not a useful new threat boundary. The normal synchronous extension mutation order is correct.
- Capability ceilings use active tool capability unions, including `exec` expansion, not resolved per-call grants. The delegation spec explicitly defines that tradeoff at lines 297-321. Child store/mode inheritance preserves matching rule denials. A child's ordinary file edits still cause P2.
- Plan approval returns an approval result without changing the mode at `tools/plan-present.ts:24-26,63-66`. This is an explicit implementation limit, not an unexpected grant. Plan mode conservatively blocks unknown contracts via their full capability set. Background-handle calls are also blocked under plan because bash retains `exec`, a restriction/UX issue rather than an escalation.
- Host user permission projection and `APEX_CODE_POLICY_PATH` loss across sandbox startup are covered by the parent's `config-projection-probe.ts` and `.log`. I independently checked `sandbox/cli-launch.ts:146-228,281-343`, `config.ts:550-555`, and the real main constructor. The dropped custom-policy claim requires no equivalent policy at the default OS path. Standard `/etc/apex-code/policy.json` is not lost by this argument.

## Positive controls

- All eight precedence sources are ordered explicitly; persisted source spoofing cannot change the source assigned at load.
- Malformed/unreadable configuration blocks rather than silently removing restrictions. Missing files are the deliberate empty-store case.
- Explicit matching managed policy survives bypass; plan's mutating floor survives managed allows.
- No responder, cancelled prompts, and handler errors fail closed.
- The actual CLI installs the gate after extension and declarative-hook mutation. A nonblocking hook cannot directly substitute approval for the gate.
- Child stores read live parent rules, reject file-backed API updates, and never forward the parent responder. Depth and capability checks occur before child construction.
- Bash scoped allows reject common substitution, redirection, and chained unrelated-command attacks. The remaining problems are asymmetric deny handling and lossy normalization, not absence of a parser.
